ATSolver: Agentic Tuning of Sparse Linear Solvers with Numerical Feedback

Mingke Tian, Yiyun Chen, Ruipeng Li, Tianshi Xu, Yuanzhe Xi

Department of Mathematics, Emory University · Lawrence Livermore National Laboratory

AbstractResultsFull-size figure ↗BibTeX
Problem
Solver and preconditioner configuration for sparse linear systems
Benchmark
35 matrices from 32 provenance families (SuiteSparse, MFEM)
Key idea
The language model proposes; trusted code verifies
Status

Summary

ATSolver treats solver configuration as a sequential decision under an explicit workload contract. A frozen language model emits one typed solver-workflow action at a time, while trusted code alone decides legality, runs the solver, recomputes the residual on the original system, and accounts for time and memory. Under matched budgets, the controller accepts more workloads than independent sampling and changes its setup investment with the number of right-hand sides. The evaluation also records where it does not help, and the extra search cost it pays.

Abstract

Choosing a solver and preconditioner for a sparse linear system depends on the matrix, the required accuracy, and the available time and memory. A growing body of work wraps a language model around this choice in a propose–execute–revise loop, but the value of execution feedback is rarely separated from the value of drawing more samples. We formulate sparse-solver configuration as a feasibility-first sequential decision problem under an explicit workload contract: tolerance, coverage, resource limits, proposal and trusted-execution budgets, and permitted lifecycle operations. We introduce ATSolver, a verifier-grounded controller in which a frozen language model emits typed workflow actions. Trusted code retains sole authority over legality, execution, residual verification on the original system, resource accounting, and numerical state. On 35 sparse systems from 32 provenance families, ATSolver accepts 78 of 105 single-system runs, against 74 for direct Best-of-3 at the same three-proposal budget. It also needs 46% less trusted numerical work to reach a first accepted configuration than the package default. When the number of right-hand sides grows to 32, it satisfies 72 of 105 batch workloads against 50 for an expert amortization rule. A fixed-parent intervention shows that a richer structured verifier record does not improve one-step repair over a scalar summary. We report search overhead and unexecuted components alongside every positive result.

1Motivation

Solver configuration is usually framed as a decision for one matrix–right-hand-side pair \((A,b)\). In deployment, the numerical problem comes with a contract: a requested tolerance, time and memory limits, available hardware and software, and a lifecycle. The lifecycle may contain one solve, a batch of right-hand sides sharing a matrix, or an ordered sequence of related systems. These fields interact. A setup that is too expensive for one solve may pay for itself over a batch, and a fast preconditioner may violate a memory limit. The unit of study is therefore a workload, not an isolated matrix.

Language-model agents already revise programs and optimization decisions after observing execution feedback. For sparse linear algebra the open question is narrower. Under matched proposal and execution budgets, does verifier-generated feedback improve the proposal policy beyond drawing more independent samples? And can it do so while numerical correctness and resource accounting stay under trusted control? A backend convergence flag, a model explanation, or a retrieved case does not by itself establish the user’s residual, coverage, memory, or deadline requirements.

Contributions
  • Workload-contract formulation and protocol. Configuration is posed as a feasibility-first sequential decision with explicit acceptance, coverage, resource, and budget constraints. Every proposal, gate decision, execution, verification, and state transition is logged, so each reported improvement can be traced to a specific charged decision.
  • Verifier-grounded controller. A typed interface separates language-model proposals from numerical authority. Compared policies differ only in the projection that builds the next decision state, which makes one-shot, independent, and feedback-conditioned search directly comparable.
  • Controlled evidence. The evaluation covers end-to-end configuration, a matched information ladder with a fixed-parent intervention, and batch-aware setup selection at three batch sizes. Positive and negative results are reported with the same paired uncertainty procedure.

2Workload contract

A sparse linear workload bundles the systems to be solved with what a solution must satisfy and what it may cost:

\[\mathcal{W}=(\mathcal{L},\mathcal{R},\mathcal{H},\mathcal{B}),\qquad \mathcal{L}=\Big(\big(A_t,(b_{t,k})_{k=1}^{K_t}\big)\Big)_{t=1}^{T},\qquad \mathcal{B}=(B_{\mathrm{prop}},B_{\mathrm{exec}},B_{\mathrm{wall}},B_{\mathrm{timeout}},B_{\mathrm{mem}})\]

where

\(\mathcal{L}\)
\(T\) ordered system positions; position \(t\) holds the operator \(A_t\) and its \(K_t\) required right-hand sides
\(\mathcal{R}\)
the requirement record: required index set, tolerances, coverage rule, admissible workflow components, and permitted lifecycle operations
\(\mathcal{H}\)
the hardware and software environment
\(\mathcal{B}\)
caps on language-model proposals, trusted executions, workload deadline, per-action timeout, and peak memory

Acceptance

For an attempted solution \(\hat{x}_{t,k}\), trusted code recomputes the relative residual on the original system and accepts only if it meets the contract tolerance:

\[\rho_{t,k}=\frac{\lVert A_t\hat{x}_{t,k}-b_{t,k}\rVert_2}{\max\{\lVert b_{t,k}\rVert_2,\ \epsilon_b\}},\qquad z_{t,k}=\mathbf{1}\big\{\hat{x}_{t,k}\ \text{exists, is finite and method-valid, and}\ \rho_{t,k}\le\tau_{t,k}\big\}\]

Missing solutions, numerical failures, gate rejections, timeouts, crashes, and resource-terminated executions all have \(z_{t,k}=0\). Workload coverage and satisfaction are then

\[\begin{gathered}\operatorname{Coverage}(\mathcal{W})=\frac{\sum_{(t,k)\in\mathcal{I}}w_{t,k}\,z_{t,k}}{\sum_{(t,k)\in\mathcal{I}}w_{t,k}},\\[4pt] \operatorname{Sat}(\mathcal{W})=\mathbf{1}\big\{\operatorname{Coverage}\ge\gamma,\ N_{\mathrm{prop}}\le B_{\mathrm{prop}},\ N_{\mathrm{exec}}\le B_{\mathrm{exec}},\ T_{\mathrm{wall}}\le B_{\mathrm{wall}},\ M_{\mathrm{peak}}\le B_{\mathrm{mem}}\big\}\end{gathered}\]

The default contract uses equal weights and \(\gamma=1\): every mandated solve must pass. Library convergence flags, exit status, model confidence, and retrieved experience cannot override these definitions. Satisfaction is the primary outcome, and favorable runtime never compensates for a contract violation.

Three costs

The cost of searching for a workflow is kept separate from the cost of deploying the selected one. The controller cost \(C_{\mathrm{ctrl}}\) charges the trusted work of every admitted execution, including failed ones. \(C_{\mathrm{first}}\) is the same sum up to the first accepted execution. \(C_{\mathrm{deploy}}(a^\star)\) is the cost of running the returned incumbent alone. In the batch regime, a candidate may build its setup once and reuse it across the declared right-hand sides:

\[C^{\mathrm{M}}_{\mathrm{deploy}}(a;K)=C_{\mathrm{pre}}(a)+C_{\mathrm{setup}}(a)+\sum_{k=1}^{K}\big[C_{\mathrm{solve},k}(a)+C_{\mathrm{verify},k}(a)\big]\]

The choice is therefore between workflows with different setup and marginal-solve costs. A lightweight configuration has a cheap setup and expensive solves. An expensive preconditioner or factorization pays off only once it is amortized over enough right-hand sides. The experiments use regime S (\(T=1,K=1\)) and regime M (\(T=1,K>1\)); ordered sequences (regime Q, \(T>1\)) are a secondary extension.

3The ATSolver controller

ATSolver is one frozen language-model policy placed over a registered portfolio of classical solver workflows. The same policy issues the initial recommendation and every revision. Before each charged decision \(j\), a trusted projector builds the public decision state

\[d_j=P_{\mathrm{arm}}(\mathcal{W},\xi_j)=\big(c_j,\ m^{\mathrm{arm}}_j,\ \mathcal{A}_j,\ \beta_j\big)\]

where

\(\xi_j\)
the complete trusted state, which the model never sees
\(c_j\)
the identity-withheld workload card: contract-relevant matrix features, structural checks, inexpensive probes, backend capabilities
\(m^{\mathrm{arm}}_j\)
the history that the experimental arm is allowed to expose
\(\mathcal{A}_j\)
the state-dependent legal action domain
\(\beta_j\)
the remaining proposal and execution budgets

The projection \(P_{\mathrm{arm}}\) is the single point of intervention in every feedback experiment. An independent arm sees no earlier proposals or outcomes. A state-only arm sees tried actions and remaining budgets. A scalar arm adds residual, coverage, runtime, and memory. A structured arm adds the typed verifier record and a deterministic diagnosis. Card, model, prompt, action schema, and budgets stay fixed, so differences between arms cannot come from the numerical runtime or the action space.

Guarded propose–execute–verify–revise loop

\[a_j\sim\pi_\theta(\cdot\mid d_j),\qquad \eta_j=G(\mathcal{W},\xi_j,a_j),\qquad y_j=E(\mathcal{W},\xi_j,a_j),\qquad e_j=V(\mathcal{W},a_j,y_j),\qquad \xi_{j+1}=U(\xi_j,a_j,\eta_j,e_j,\delta_j)\]
  1. Propose. The policy emits exactly one typed action or Stop. Every call consumes a proposal slot; malformed, duplicate, or unaffordable outputs are recorded, never silently repaired or resampled.
  2. Gate. \(G\) checks schema, method preconditions, parameter constraints, backend support, duplicates, lifecycle state, and the remaining contract. A rejection costs a proposal slot but no execution.
  3. Execute and verify. The worker \(E\) runs admitted actions; the verifier \(V\) recomputes original-system residuals and applies coverage, time, and memory constraints. A clean exit or a convergence flag is evidence, not acceptance.
  4. Diagnose and update. A deterministic map \(\delta_j=D(a_j,\eta_j,e_j)\) names the failure category without choosing the next solver. \(U\) updates the ledgers and replaces the incumbent only under a frozen lexicographic rule: satisfaction first, then deployment cost.

Action portfolio

All methods select from one frozen native portfolio. It contains HYPRE workflows using PCG, GMRES, FGMRES, or BiCGSTAB, each with no preconditioner or with AMG, ILU, or FSAI, plus a serial SuperLU direct factorization where the contract permits. Branch-specific schemas expose only the parameters valid for the chosen workflow. The portfolio spans low- and high-setup configurations, so a policy must trade setup investment against per-solve cost. The model manipulates typed intent, never numerical objects. Every request, output, gate decision, execution, verification, and budget change is written to a hash-bound ledger that supports replay.

4Experimental setup

Workloads. 35 sparse matrices: 29 from the SuiteSparse collection and six finite-element systems assembled with MFEM, organized into 32 provenance families. A provenance group holds an original matrix together with its transformed versions, generated right-hand sides, and parameterized relatives, and no group is split across development and evaluation. Seven generated systems from four disjoint families are used only for implementation checks and calibration. Matrix names and collection identifiers are withheld from the model-visible card.

Contract and repetitions. The completed campaign uses one contract stratum: tolerance \(\tau=10^{-8}\), a 1 GiB peak-memory charge, and a 30 s per-action limit. Each model-based condition is repeated three times per workload, giving 105 runs per policy. Repetitions are nested within matrices rather than counted as additional matrices.

Controller and backend. A frozen gpt-5.6-terra proposal policy, native HYPRE 3.1 iterative workflows, and serial SuperLU 7 factorization. Within a matched comparison, conditions share the workload card, action grammar, backend, model and decoding settings, budgets, timeouts, and memory caps.

Research questions.

  1. RQ1, end-to-end configuration. Single-system workloads, comparing ATSolver with same-budget direct and expert-guided Best-of-3 search, plus lower-budget package-default and one-shot references.
  2. RQ2, information-conditioned search. The matched ladder from independent to structured feedback at a common 3/3 budget, and a fixed-parent intervention that holds one failed trial fixed and varies only what the model sees.
  3. RQ3, batch-aware setup selection. One matrix with \(K\in\{2,8,32\}\) right-hand sides. Every right-hand side must pass, and the question is whether the selected setup class changes with \(K\).

Endpoints and statistics. The primary outcome is workload-level contract satisfaction over all assigned runs. Secondary outcomes are restricted mean trusted work to first acceptance (RMW, unsuccessful runs right-censored at a common 180 s horizon), complete online search wall time, and the selected workflow’s deployment time \(T_{\mathrm{dep}}=T_{\mathrm{pre}}+T_{\mathrm{setup}}+T_{\mathrm{solve}}\). Deployment comparisons use only runs satisfied by both policies, and always state that denominator. Intervals are 95% percentile intervals from a 10,000-sample hierarchical bootstrap over provenance group, matrix, and paired repetition.

ATSolver accepts the most runs and reaches its first accepted action with the least trusted numerical work; these figures include unsuccessful runs at the common horizon. Its complete online search is longer, 26.28 s against 21.64 s for direct Best-of-3. A lower cost to the first accepted action and a longer complete search therefore coexist, and neither is a net saving for a single subsequent deployment.

On jointly satisfied runs, the selected deployment phase is 0.6153 s against 0.7428 s for direct Best-of-3 (74 pairs over 26 matrices). This is an observed 17.2% reduction, but it is not statistically resolved (\(p=0.118\)). Against expert-guided Best-of-3 the reduction is 22.0% (0.5673 s against 0.7268 s, 75 pairs over 25 matrices, \(p=0.003\)). In a separate seeded continuation, 62 of 76 initially accepted runs return a cheaper configuration. That continuation uses 419 additional proposals and does not raise final satisfaction above 78/105.

Independent proposals reach 66, 71, and 74 accepted runs over three slots; structured feedback reaches 69, 78, and 78, attaining the sequential ceiling by the second proposal. Independent sampling spends 94 of its 315 slots (29.8%) re-proposing configurations it has already tried, and no sequential arm proposes a duplicate. State-only history also removes duplicates and also reaches 78/105, so the trajectory comparison does not establish a unique benefit of the structured fields.

The fixed-parent intervention isolates content. It binds the same non-convergent GMRES trial (no preconditioner, zero initial guess, two-iteration limit), the same legal child domain, and a one-proposal budget across all four arms. Structured feedback yields 62/105 accepted next actions against 68/105 for scalar feedback, a difference of \(-5.71\) percentage points (95% CI \([-12.12,\,-0.95]\)). For these prescribed failures, the additional structured fields do not improve one-step recovery. The result is limited to this parent family and should not be read as a statement about every failure encountered during search.

Forty-six of the 72 units change setup class across batch sizes. As \(K\) grows, the controller invests in more expensive setups, most often direct factorization, and the per-right-hand-side solve time falls accordingly. The deployment savings must also be read alongside the upfront search, which is longer than the expert rule’s at every \(K\).

6Supporting studies

These studies use different populations, budgets, or protocols and are not pooled with RQ1–RQ3.

  1. Retrieved knowledge and experience. All five retrieval contexts satisfy 78/105. Adding retrieved experience to knowledge lowers the selected deployment cost by 19.0% (ratio 0.810), and by 14.5% (ratio 0.855) against a byte-matched static context; both intervals lie below one. Retrieval audits record zero overlap with evaluation families and no online updates. The experience arm uses more tokens.
  2. Resource and accuracy sweeps. Separate sweeps over memory caps of 192, 512, and 4096 MiB and tolerances of \(10^{-10}\), \(10^{-8}\), and \(10^{-6}\). Three-proposal ATSolver satisfies more runs than a single call in every condition. The fixed expert policy is slightly higher overall, so the sweeps do not show that ATSolver dominates the expert.
  3. Related-system sequences (regime Q). Over four-position sequences, ATSolver completes 72/105 under both operator schedules, against 63/105 and 69/105 for a matched prescribed-rebuild control. Conditional deployment cost is not lower.
  4. Matrix-image channels. An audit of the four-channel study found that no image panels reached the model in any condition. Those results are therefore kept as a diagnostic and are not used as evidence about images.

7Discussion and limitations

The trusted boundary is what makes these questions answerable. Because workload, action space, executor, verifier, and budget are held fixed, the evaluation can ask which part of the controller does the work, not only whether it wins. Three findings stand out. Feasibility gains over same-budget sampling are real but modest. Removing repeated proposals accounts for much of the advantage of sequential search, and richer diagnostic content does not improve one-step repair. The clearest workload-level effect appears in the batch regime, where the controller shifts toward expensive reusable setups as \(K\) grows.

  1. The completed campaign realizes a single contract stratum, so the main comparisons cannot say how the effects move with tolerance or resource pressure.
  2. Search consumes more wall time and more provider tokens than the baselines; a reader who budgets tokens rather than trusted numerical work may reach a different conclusion for a single solve.
  3. In RQ3 the controls choose from a smaller action space, which limits policy-level attribution; a same-action-space comparison remains future work.
  4. Residual acceptance does not certify the physical model, the discretization, or the forward error, and hardware-specific timings need not transfer across platforms.

The contract, the typed action grammar, and the per-proposal audit ledger are released so the remaining experiments can be run against the same frozen protocol.
