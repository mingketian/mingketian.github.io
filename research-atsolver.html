ATSolver: Agentic Tuning of Sparse Linear Solvers with Numerical Feedback

Mingke Tian, Yiyun Chen, Ruipeng Li, Tianshi Xu, Yuanzhe Xi

Paper (PDF) ↗Full-size figure ↗

Picking a solver and preconditioner for a large sparse linear system is usually done by expert intuition or brute-force search. ATSolver hands the choice to an LLM agent, but never lets the agent decide what counts as solved: every proposal passes a legality gate, runs on a real numerical worker, and is accepted only if an independent verifier confirms the residual.

1Problem setup

Each request is a sparse linear system together with a contract that says what a good answer must satisfy and what it may cost:

\[A\mathbf{x}=\mathbf{b},\qquad A\in\mathbb{R}^{n\times n}\ \text{sparse},\qquad \mathcal{W}=(L,\,R,\,H,\,B)\]

where

\(L\)
the regime: matrix size, structure, and number of right-hand sides
\(R\)
requirements: target accuracy and coverage
\(H\)
available hardware: CPU, GPU, and memory
\(B\)
budgets: time, memory, and number of trials

The task is to find a configuration that meets \(R\) within \(B\), using as few trials as possible.

2What the agent sees

The agent never receives raw matrix entries. It receives a public decision state built from the matrix and from previous attempts:

\[s_k=\big(\mathcal{V}(A),\ \mathcal{C}(A),\ \mathcal{H}_k\big)\]

where

\(\mathcal{V}(A)\)
multimodal channel views of the sparsity pattern: natural ordering, reverse Cuthill–McKee ordering, and positive and negative entries
\(\mathcal{C}(A)\)
a numeric workload card: symmetry, scaling, evidence of positive definiteness, and sparsity statistics
\(\mathcal{H}_k\)
the history of the first \(k\) attempts, their outcomes, and diagnoses

3Actions

At each step the frozen LLM proposes one configuration, or stops:

\[a_k\in\mathcal{A}=\big\{(\text{solver},\ \text{preconditioner},\ \boldsymbol{\theta},\ \text{lifecycle})\big\}\cup\{\textsf{STOP}\}\]

where

solver
an iterative method (PCG, GMRES, FGMRES, BiCGSTAB) from hypre, or a direct SuperLU factorization
preconditioner
none, algebraic multigrid (AMG), incomplete LU (ILU), or FSAI
\(\boldsymbol{\theta}\)
the numerical parameters of the chosen methods
lifecycle
whether to build a new setup or reuse an existing one

A schema and legality gate rejects malformed or unsafe actions before anything runs; rejected proposals cost no solver time.

4Independent verification

A configuration is accepted only if the returned solution passes a residual check that the solver itself does not perform:

\[\mathbf{r}=\mathbf{b}-A\hat{\mathbf{x}},\qquad \rho=\frac{\lVert\mathbf{r}\rVert_2}{\max\!\big(\lVert\mathbf{b}\rVert_2,\ \varepsilon_b\big)}\ \le\ \tau\]

where

\(\hat{\mathbf{x}}\)
the solution returned by the numerical worker
\(\rho\)
the relative residual
\(\varepsilon_b\)
a floor that keeps the ratio defined when \(\lVert\mathbf{b}\rVert_2\) is tiny
\(\tau\)
the tolerance required by \(R\)

Failures are diagnosed (for example, a violated constraint or a stalled iteration) and written back into \(\mathcal{H}_{k+1}\). Retrieved numerical knowledge and past runs also guide proposals on new workloads.

5Results

  • 75 / 105configurations accepted on 35 matrices, versus 64 / 105 for matched-budget Best-of-6
  • 30.1%lower replay solve time
  • 19 → 38of 42 held-out PDE targets met once retrieval is added

6Conclusion

Grounding an LLM agent in independent numerical verification makes it a reliable solver tuner: it accepts more configurations than sampling with the same budget, finds faster ones, and generalizes better when it can retrieve past experience.
